Prove three things in three minutes: Agent conclusions have code evidence, sensitive actions have an exact human gate, and candidate patches receive auditable validation in isolation.

## 常见追问 / Common Questions

### 为什么不让模型直接用 Shell？ / Why not give the model a shell?

> Shell 把读取、执行、网络和写入混合成过宽权限。IssueLens 让模型只表达五种结构化只读意图，再由安全内核校验路径、大小与返回证据；测试执行是独立、人工审批后的容器能力。
>
> A shell combines reading, execution, network, and writes into overly broad authority. IssueLens lets the model express only five structured read-only intents while the safety kernel validates paths, sizes, and returned evidence; test execution is a separate container capability available only after human approval.

### Checkpoint 如何避免恢复时重复副作用？ / How does resume avoid repeated side effects?

> Checkpoint 在每个完成步骤后记录下一步、证据、观察与累计预算，并绑定 Issue 和仓库快照。恢复从 `next_step` 开始；输入漂移或完整性失败会拒绝。Agent 分析阶段本身只读，补丁验证又是独立命令，因此恢复不会重放真实写入。
>
> After each completed step, the checkpoint records the next step, evidence, observations, and accumulated budgets and binds the Issue and repository snapshot. Resume starts at `next_step`; input drift or integrity failure is rejected. Agent analysis itself is read-only, and patch validation is a separate command, so resume does not replay a real write.

### Docker 是否足够安全？ / Is Docker sufficiently secure?

> 对作品集 MVP，固定镜像、断网、非 root、只读挂载、无 Capabilities 和资源上限形成明确的最小权限边界；但普通 Docker 仍共享宿主内核，不应包装成生产级多租户恶意代码沙箱。生产化需要微虚机或独立 VM、依赖供应链控制和独立安全评审。
>
> For a portfolio MVP, a pinned image, no network, non-root execution, read-only mounts, dropped capabilities, and resource limits form a clear least-privilege boundary. Ordinary Docker still shares the host kernel and must not be presented as a production multi-tenant hostile-code sandbox. Production use needs microVMs or dedicated VMs, dependency-supply-chain controls, and independent security review.

### 为什么需要隐藏测试？ / Why use hidden tests?

> 如果候选补丁只针对可见复现测试过拟合，隐藏测试可以提供独立信号。当前隐藏测试由仓库外 Bundle 注入，不进入目标源码，但仍是项目维护者编写的合成 Grader；真实评测需要从历史修复和维护者测试中独立构建。
>
> A candidate patch may overfit the visible reproduction test; hidden tests provide an independent signal. The current hidden bundle is injected from outside the target source, but it is still a synthetic grader authored by the project maintainer. Real evaluation requires independently constructed historical fixes and maintainer tests.

### 这是 Agent 还是普通脚本？ / Is this an Agent or a regular script?

> Issue 分析部分是可替换 Policy 驱动的多步工具循环，包含观察、检索、证据累积、状态与停止条件；安全 Harness、审批和测试验证故意保持确定性。设计重点不是让所有东西都由模型决定，而是让 Agent 只负责适合不确定推理的部分。
>
> Issue analysis is a replaceable-policy-driven multi-step tool loop with observations, retrieval, evidence accumulation, state, and stop conditions; the safety harness, approval, and test validation are intentionally deterministic. The design does not make everything model-driven; it gives the Agent only the work suited to uncertain reasoning.

### 下一步是什么？ / What comes next?

> 下一步是 30–50 个时间切分公开 Issue、独立 Reproduction/Hidden Grader、依赖构建阶段、真实 Agent-generated Resolved@1 与成本/失败报告；产品侧则是可信身份和默认关闭的 GitHub Draft PR 发布。
>
> Next comes 30–50 time-split public Issues, independent reproduction/hidden graders, a dependency-build phase, real Agent-generated Resolved@1 with cost/failure reporting, plus trusted identity and default-disabled GitHub Draft PR publication on the product side.

## 收尾句 / Closing Statement

> 这个项目最想证明的不是我会调用模型，而是我能把 Agent 的不确定性放进可验证的工程系统：证据可追溯、权限最小化、运行可恢复、危险动作精确审批、测试独立验证、结果可以复核。
>
> The main point is not that I can call a model. It is that I can place Agent uncertainty inside a verifiable engineering system: traceable evidence, least privilege, resumable runs, exact approval for sensitive actions, independent test validation, and reviewable results.
